## Что сделано

В КР №1 был консольный интернет-магазин. КР №2 добавляет к тому же проекту настольный интерфейс JavaFX, сохраняя PostgreSQL, сущности и бизнес-правила.

Основная сущность — заказ. Покупатель связан с заказом, а товары входят в него через позиции. Поэтому центральный экран показывает заказы, а форма позволяет выбрать покупателя и товары по названиям без ручного ввода внешних ключей.

Реализованы таблицы заказов, покупателей и товаров; добавление покупателей и товаров; создание, просмотр, редактирование и подтверждённое удаление заказов; смена статусов; поиск, два фильтра и две сортировки; семь показателей статистики; Excel-экспорт текущего списка. Ключевые окна находятся в FXML, оформление — в CSS.

Полный CRUD сделан для основной сущности — заказа. Редактирование и удаление справочников дополнительно не добавлялись: этого не требует ТЗ КР №2. Авторизация, Spring, REST, Android, корзина и настоящая платёжная интеграция также не добавлялись.

Существующие консольные классы сохранены для совместимости КР №1 и её тестов. Основной запуск новой работы открывает JavaFX.

## Как запустить

Открой корень исходного проекта `Desktop/study/study-java`. Docker Desktop должен работать. На этом компьютере Java 21 и Maven 3.9.9 найдены внутри IntelliJ IDEA; системная Java в PATH была версии 17.

1. Проверь `.env`: настройки должны указывать на PostgreSQL магазина, а не на учебную БД `student_hub`.
2. Запусти `docker compose up -d --wait`.
3. Запусти `powershell -ExecutionPolicy Bypass -File .\run.ps1` или `mvn javafx:run`, если Java 21 и Maven настроены в PATH.
4. В IntelliJ IDEA можно открыть `pom.xml`, выбрать JDK 21 и выполнить Maven goal `javafx:run`.

В подготовленном `.env` используется порт `15432`: стандартный `5432` занят другой локальной PostgreSQL. Опубликованный порт Compose и порт JDBC должны совпадать. Шаблон `.env.example` содержит стандартный `5432`; порт меняется через настройки, а не в Java-коде.

Остановка: `docker compose down`. Удаление volume при остановке не нужно: данные должны сохраняться.

Файлы: [инструкция запуска](../README.md), [скрипт Windows](../run.ps1), [Maven](../pom.xml), [Docker Compose](../compose.yaml), [шаблон настроек](../.env.example).

## Как устроено приложение

Путь действия пользователя:

```text
FXML / элементы интерфейса
          ↓
Controller — принимает действие пользователя
          ↓
Service — проверяет бизнес-правила
          ↓
Repository / JDBC — выполняет SQL
          ↓
PostgreSQL — хранит записи и ограничения
```

После завершения операции контроллер обновляет отображаемый список. SQL не находится в кнопках, а правила заказов не копируются в каждое окно.

[StoreApplication](../src/main/java/ru/mirea/store/fx/StoreApplication.java) создаёт главное окно и Scene, загружает FXML, подключает CSS и запускает загрузку данных. [StoreLauncher](../src/main/java/ru/mirea/store/fx/StoreLauncher.java) — отдельная точка входа для упаковки.

[StoreServices](../src/main/java/ru/mirea/store/fx/StoreServices.java) связывает компоненты: читает параметры БД, создаёт JDBC-репозитории и передаёт их сервисам. Контроллер получает готовые сервисы. Это позволяет использовать существующую логику КР №1 без её переписывания.

Прямое JDBC-подключение делает [DatabaseManager](../src/main/java/ru/mirea/store/config/DatabaseManager.java). [DatabaseConfig](../src/main/java/ru/mirea/store/config/DatabaseConfig.java) читает окружение и `.env`; окружение имеет приоритет. Пароль больше не задан строкой по умолчанию в Java-классе. При отсутствии внешнего пароля запуск сообщает об ошибке.

## Главное окно и таблицы

Открой рядом [разметку main.fxml](../src/main/resources/ru/mirea/store/fx/main.fxml) и [MainController](../src/main/java/ru/mirea/store/fx/controller/MainController.java).

Сверху находятся обновление, статистика и экспорт. Ниже — вкладки заказов, покупателей и товаров. На вкладке заказов есть блок поиска и фильтров, кнопки CRUD, таблица и блок смены статуса.

Таблица заказов показывает номер, покупателя, статус, дату создания, сумму и примечание. Вместо внешнего ключа покупателя отображается ФИО. Для покупателей доступны ФИО, email, телефон, активность и дата регистрации; для товаров — SKU, название, цена, остаток и активность.

`initialize()` настраивает элементы и столбцы. `refresh()` загружает свежие данные из БД. Результат помещается в `ObservableList`, который назначается TableView. Это коллекция JavaFX, которую таблица умеет наблюдать.

`selectionChanged()` отслеживает выбранную строку. При отсутствии выбора действия над заказом отключены. Редактирование доступно только для нового заказа; удаление — для нового или отменённого. В списке статусов показываются только разрешённые следующие состояния.

После изменения данных выполняется повторная загрузка. Поиск, фильтры и направление сортировки остаются выбранными, поэтому новая запись может не появиться в таблице, если она не подходит под текущие условия. Кнопка «Сбросить» возвращает полный список.

## Заказ: создание, редактирование, удаление

Файлы: [форма заказа](../src/main/resources/ru/mirea/store/fx/order-form.fxml), [OrderFormController](../src/main/java/ru/mirea/store/fx/controller/OrderFormController.java), [CustomerOrderService](../src/main/java/ru/mirea/store/service/CustomerOrderService.java).

При добавлении открывается отдельное модальное окно. Пользователь выбирает активного покупателя и активные товары, вводит количества и примечание. Нажатие «Добавить / заменить» помещает товар в таблицу позиций. Повторный выбор того же товара заменяет его количество, а не создаёт дубликат. «Убрать выбранную позицию» удаляет строку из формы.

Итог рассчитывается как сумма `цена × количество` по всем позициям. Введённые в форму данные ещё не являются записью в БД: сохранение происходит только по кнопке «Сохранить».

`save()` переводит строки формы в `OrderItemInput` и вызывает `createOrder()` либо `updateNew()` сервиса. Сервис проверяет активность покупателя и товаров, количества, отсутствие дубликатов, непустой заказ и длину примечания. Репозиторий сохраняет заказ и позиции в одной транзакции.

При редактировании форма заполняется текущим покупателем, позициями и примечанием. Существующая логика КР №1 при сохранении редактируемого нового заказа берёт цены из актуального каталога; форма прямо сообщает об этом. При обычном просмотре старого заказа используются сохранённые цены позиций.

Удаление в `MainController.deleteOrder()` сначала показывает подтверждение. Отмена ничего не меняет. После подтверждения вызывается `CustomerOrderService.delete()`. Даже если кнопка была доступна, сервис и репозиторий повторно проверяют статус: запись могла измениться после загрузки таблицы.

Просмотр открывает [order-details.fxml](../src/main/resources/ru/mirea/store/fx/order-details.fxml) через [OrderDetailsController](../src/main/java/ru/mirea/store/fx/controller/OrderDetailsController.java). Видны контактные данные покупателя, позиции, SKU и названия товаров, количества, исторические цены, суммы, примечание и даты жизненного цикла.

## Статусы и остатки

Файлы: [OrderStatus](../src/main/java/ru/mirea/store/model/OrderStatus.java), [сервис заказов](../src/main/java/ru/mirea/store/service/CustomerOrderService.java), [JDBC заказов](../src/main/java/ru/mirea/store/repository/jdbc/JdbcCustomerOrderRepository.java).

Разрешённая последовательность: `NEW → PAID → SHIPPED → DELIVERED`. Отмена разрешена из `NEW` и `PAID`. Отправленный или доставленный заказ нельзя редактировать или удалить; он остаётся в истории.

При переходе в `PAID` репозиторий блокирует нужные товары, проверяет остатки и уменьшает их. Если хотя бы одного товара недостаточно, вся операция откатывается. Это не настоящий платёж: это бизнес-операция смены статуса из КР №1.

Отмена оплаченного заказа восстанавливает его количества на складе. Отмена нового заказа остатки не меняет. Даты оплаты, отправки, доставки и отмены формирует приложение; пользователь не вводит их вручную.

Транзакция означает «всё или ничего»: статус заказа, остатки и связанные изменения либо сохраняются вместе, либо не сохраняются. Иначе можно было бы получить оплаченный заказ с некорректным складом.

## Поиск, фильтры и сортировка

Основной файл: [OrderQueryService](../src/main/java/ru/mirea/store/service/OrderQueryService.java). Элементы управления и передача критериев находятся в [MainController](../src/main/java/ru/mirea/store/fx/controller/MainController.java).

Поиск выполняется по части ФИО покупателя либо названия товара, без учёта регистра. Поле поиска выбирается пользователем. Пустая строка не ограничивает список.

Два фильтра — статус и диапазон дат создания. Границы периода включаются. Обе даты должны быть заполнены вместе; начальная дата не должна быть позже конечной.

Сервис применяет поиск и фильтры одновременно к одному загруженному списку. Например, «Петров» + «Новый» + период означает только новые заказы подходящего покупателя за этот период. После этого результат сортируется.

Сортировка — по дате создания либо общей сумме, по возрастанию или убыванию. Используется существующий метод `CustomerOrderService.sort()`. При равных значениях дополнительным критерием служит ID заказа. Заголовки таблицы не запускают отдельную текстовую сортировку: пользователь выбирает параметры в блоке над таблицей, поэтому деньги сортируются как числа, а даты — как даты.

Поиск в GUI выполняется по записям, загруженным из PostgreSQL. Кнопка «Обновить данные» повторно читает БД. Это прямое JDBC-приложение, а не REST-клиент.

## Проверка ввода

Открой [InputValidator](../src/main/java/ru/mirea/store/validation/InputValidator.java). Проверки повторно используются сервисами и формами.

Проверяются обязательные поля, формат и диапазоны чисел, длины строк, email, телефон, SKU, корректность периода, активность и существование связанных объектов, правила статусов и позиций. Ограничения взяты из КР №1: например, примечание до 500 символов, ФИО до 200, SKU до 64, название товара до 300.

Добавление справочников: [catalog-form.fxml](../src/main/resources/ru/mirea/store/fx/catalog-form.fxml), [CatalogFormController](../src/main/java/ru/mirea/store/fx/controller/CatalogFormController.java), [CustomerService](../src/main/java/ru/mirea/store/service/CustomerService.java), [ProductService](../src/main/java/ru/mirea/store/service/ProductService.java).

Перед сохранением сервисы проверяют уникальность email и SKU. UNIQUE-ограничения остаются также в БД: проверка приложения не заменяет защиту от параллельной записи другим клиентом.

Неверные числовые значения сообщаются до отправки SQL. Ошибка сервиса показывается диалогом, а форма сохраняет введённые значения. После ошибки сохранения она снова доступна для исправления.

[Ui.error()](../src/main/java/ru/mirea/store/fx/util/Ui.java) отделяет ошибки ввода, бизнес-правил, доступа к БД и экспорта. Пользователь видит сообщение вместо stack trace; технические подробности остаются в журнале. SQL-ошибка получает общее сообщение о подключении, уникальности и связанных записях.

## Статистика и экспорт

Статистика: [FXML](../src/main/resources/ru/mirea/store/fx/statistics.fxml), [StatisticsController](../src/main/java/ru/mirea/store/fx/controller/StatisticsController.java), [StatisticsService](../src/main/java/ru/mirea/store/service/StatisticsService.java), [JdbcStatisticsRepository](../src/main/java/ru/mirea/store/repository/jdbc/JdbcStatisticsRepository.java).

Отображаются существующие семь показателей: количество покупателей, товаров, единиц на складе и заказов; распределение заказов по статусам; выручка доставленных заказов; количество товаров без остатка. ТЗ требует минимум пять, поэтому новых расчётов добавлять не понадобилось.

Показатели относятся ко всей БД, даже если список заказов отфильтрован. При каждом открытии окна статистика загружается заново. Выручка считается по сохранённым ценам позиций доставленных заказов.

Экспорт: [ExcelExporter](../src/main/java/ru/mirea/store/export/ExcelExporter.java), [StoreExportData](../src/main/java/ru/mirea/store/export/StoreExportData.java), метод `export()` в [MainController](../src/main/java/ru/mirea/store/fx/controller/MainController.java).

FileChooser позволяет выбрать имя и путь `.xlsx`. Сохраняются текущие отображаемые заказы в их порядке и соответствующие позиции; справочники и статистика относятся ко всей базе. Это прямо указано в окне. Отмена FileChooser не создаёт файл.

Новый `exportToFile()` принимает точный выбранный путь. Старый `export()` с каталогом оставлен для существующей консольной работы. Apache POI формирует пять листов: покупатели, товары, заказы, позиции и статистика. Цены и суммы записываются числовыми ячейками, а не строками.

## FXML, CSS и фоновые задачи

[FXML-файлы](../src/main/resources/ru/mirea/store/fx/main.fxml) описывают расположение элементов. `fx:id` позволяет связать элемент с полем контроллера, помеченным `@FXML`. `onAction="#save"` связывает кнопку с методом `save()`.

Контроллер задаётся загрузчику через `FXMLLoader.setController()`, поэтому в разметке не указан `fx:controller`. Это позволяет передать сервисы в конструктор. Комбинировать оба способа в одном файле не нужно.

[store.css](../src/main/resources/ru/mirea/store/fx/store.css) задаёт фон, шрифты, кнопки, таблицы, поля ввода и оформление диалогов. Цвет выбранной строки отличается, текст остаётся читаемым. FlowPane переносит группы элементов на следующую строку при уменьшении ширины; таблицы растягиваются вместе с окном.

[Ui.run()](../src/main/java/ru/mirea/store/fx/util/Ui.java) запускает JDBC и экспорт через `Task` в отдельном потоке. JavaFX Application Thread занимается интерфейсом. Обработчики успешного завершения и ошибки возвращаются на поток JavaFX; только там изменяются таблицы и показываются диалоги.

Пока запрос выполняется, соответствующая форма или главное окно отключены, чтобы не отправлять повторное сохранение. После завершения управление возвращается пользователю. Фоновый исполнитель останавливается вместе с приложением.

## База данных

Файлы: [схема](../docker/db/init/01-schema.sql), [исходные тестовые данные](../docker/db/init/02-seed.sql), [создание отдельной тестовой БД](../docker/db/init/00-create-test-db.sql), [ER-диаграмма](../docs/online-store-er-diagram.puml).

Таблицы `customers`, `products`, `customer_orders`, `order_items` сохранены из КР №1. Внешние ключи поддерживают связи. CHECK и UNIQUE защищают допустимые значения, статусы и уникальность. Суммы заказов рассчитываются по позициям, цены позиций хранятся отдельно от актуальных цен каталога.

Репозитории используют `PreparedStatement`: пользовательские значения передаются параметрами SQL. `try-with-resources` закрывает подключения, запросы и результаты даже при исключении.

Скрипты Docker инициализируют пустой том. Повторный запуск существующего тома не сбрасывает записи. Тесты работают с отдельной БД и очищают её, поэтому параметры рабочей и тестовой БД нельзя смешивать.

## Проверки и ограничения

Проверены компиляция Java 21 и 36 тестов без ошибок и пропусков. Среди них проверки репозиториев PostgreSQL, правил заказов, экспорта, совместного поиска и фильтров. [JavaFxIntegrationTest](../src/test/java/ru/mirea/store/integration/JavaFxIntegrationTest.java) загрузил все FXML-окна и создал/отредактировал заказ через кнопки формы на отдельной тестовой БД.

В существующем тесте сохранения покупателя устранено нестабильное сравнение времени: PostgreSQL хранит микросекунды, а `LocalDateTime.now()` может содержать наносекунды. Тестовые данные теперь используют точность БД.

После повторной загрузки зависимости полная Maven-упаковка прошла успешно. Проверка Checkstyle завершилась с нулём нарушений. Итоговая полная проверка выполнена также в исходном проекте на рабочем столе: 36 тестов, упаковка и Checkstyle прошли успешно. Собранный JAR дополнительно запущен с восстановленной БД на порту 15432.

## Ответы на вопросы

**Что такое Stage?** Окно приложения. Scene — содержимое окна, Node — отдельный элемент или контейнер внутри сцены.

**Зачем FXML?** Чтобы описать структуру интерфейса отдельно от поведения и бизнес-логики.

**Что делает Controller?** Получает действия пользователя, собирает значения формы, вызывает сервисы и обновляет интерфейс. Он не выполняет SQL.

**Почему ObservableList?** TableView умеет наблюдать такую коллекцию и отображать её изменения. После чтения БД таблице назначается актуальная коллекция.

**Где правила?** В сервисах, прежде всего CustomerOrderService и InputValidator. Транзакционные операции склада находятся в JDBC-репозитории заказов; ограничения значений и связей дублируются в БД.

**Почему нельзя сохранять всё прямо в кнопке?** Тогда интерфейс смешивается с SQL и правилами, появляются дублирование и трудно проверяемые изменения. Разделение слоёв позволяет повторно использовать КР №1.

**Как обрабатывается ошибка?** Фоновая задача сообщает о неудаче, форма снова доступна, Ui показывает понятный диалог. Незавершённая транзакция откатывается.

**Почему данные БД не читаются на потоке интерфейса?** Долгий запрос заблокировал бы перерисовку окна и реакции на пользователя. Task выполняет работу в фоне.

**Как работает сортировка денег?** Сервис сравнивает BigDecimal, поэтому 100 больше 20 независимо от текстового представления.

**Зачем FileChooser?** Пользователь сам выбирает имя и место сохранения. В коде нет пути к папке разработчика.

**Чем свой проект отличается от примера?** Пример JavaFX обращается к REST backend; собственная КР №2 обязана подключаться напрямую по JDBC к своей PostgreSQL КР №1.
